   compositing scales that vector and does not turn it, so the dilution divides
   out exactly. Measured 0.025 from the right answer and 0.315 from the nearest
   wrong one (Acrobat's highlighter orange) — a factor of twelve.

=====================================================================
Draws a rectangle, selects it, raises the contextual Format tab, asserts the

  · ★ the shape was selected: `annot-select page=0 id=ObjId { num: 47 }

  · the line after the restyle: longest vertical ink run 3 px, 168 ink px of 784
  · ★★★ and the LINE ON THE PAGE is thicker: 56 → 168 ink px (3.00x, floor
    1.50x) with nothing selected

APPLICATION DEFECT FOUND — the line-width spinner cannot be DRAGGED
  → A 200 px drag across `ribbon.item.format.line_width` produced no
    `set-markup-style`. TYPING `12` into the same field produced one. So
    everything downstream of the commit works and the drag gate alone does not.
  Shape, from `crates/pdfcer-gui/src/app/markupband.rs::width`:
      let mut value = was;                       // `was` re-read every frame
      ... DragValue::new(&mut value) ...
      if (response.drag_stopped() || response.lost_focus())
         && (value - was).abs() > f64::EPSILON { commit }
    `drag_stopped()` is true on the frame the button comes UP, and on that frame
    the pointer has not moved, so `DragValue` adds nothing to a `value` that was
    just re-seeded from the document. The difference is exactly zero and the
    commit is skipped, every time.
  ⚠ REPORTED, NOT FIXED — crates/ is owned by other agents this session. Worth
    checking on the opacity field beside it, which is built the same way, and on
    any other DragValue in the shell whose backing value is re-read per frame
    rather than held as a draft.

HARNESS FINDING, worth carrying to any other band-item check
  A band item's published `ui-rect` is where the control was ALLOCATED, not
  where it is hittable: `markupband::width` pads the item out to a fixed 46 px
  with `ui.allocate_space` AFTER the widget, so a press at the rect's centre can
  land in empty ribbon. The first two runs of this check reported the dispatch
  broken for that reason. It now grabs the left third.

FALSIFICATION — the typed width set to 1 pt, thinner than the 2 pt the shape is
drawn with, so the restyle still commits and the page must NOT thicken:
  · the line after the restyle: longest vertical ink run 0 px, 0 ink px of 784
  → ★★★ THE MARK WAS RESTYLED AND THE PAGE DID NOT CHANGE. `set-markup-style`
    is in the trace ... the strip went from 56 ink px to 0: 0.00x, against a
    floor of 1.5x. **This is precisely the failure no trace assertion can see.**
  ⇒ FAIL, on the pixel branch, with the trace branch green — which is exactly
    the pair the check exists to tell apart. Restored from a copy.
