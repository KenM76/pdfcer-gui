ROW: O67 | root-cause-found | conf high
SUMMARY: The app does handle OS file drops, but the handler is position-blind by construction, so the thumbnail strip is not — and today cannot be — a drop target. `app::dropped::take` has exactly one call site, `app/frame.rs:399`, which runs at the top of the frame before any surface is drawn. It reads `ctx.input(|i| i.raw.dropped_files)`, classifies purely by file extension, and routes a `.pdf` to `Action::Open` unconditionally and a raster image to the insert-image placement window. It never asks where the pointer was, and `hovered_files` is never read anywhere in the workspace (confirmed three ways). `canvas/pagedrop.rs:62-67` states the absence verbatim: "It does not accept files dropped from Explorer." Everything downstream of the position already exists: the pages grid resolves a gap and paints a caret (`panels/pages/mod.rs:906-947`, `paint_caret` at 506-528), `pagedrag::insert_position` maps a gap to `InsertPosition` (pagedrag.rs:193-202), and `PageAction::InsertPagesFromFile { path, pages, position }` (actions/pages.rs:168-190) already carries a path AND a position to `EditSession::insert_pages`. The one genuinely missing input is the drop point, and that gap is in the windowing stack, not in pdfcer: `egui::DroppedFile` carries no position, winit 0.30.13's `WindowEvent::DroppedFile(PathBuf)` carries none, and winit's Windows `IDropTarget` implementation receives the OLE screen point and discards it as `_pt: *const POINTL` in both `DragOver` (drop_handler.rs:109) and `Drop` (drop_handler.rs:137). Because Windows OLE drag captures the mouse, no `CursorMoved` arrives during the drag either, so egui's `pointer.latest_pos()` is stale at drop time. The escape hatch is Win32 `GetCursorPos` polled per frame while `hovered_files` is non-empty — the HWND is already captured by `app::window_handle` (app/mod.rs:658-663) through the existing `raw-window-handle` dependency.

GENERALISATION: Every drop in this application is routed by ONE window-scoped, position-blind handler, so the defect class is "the drop point is discarded", and it bites in six more places. I grepped `dropped_files`, `hovered_files`, `DroppedFile`, `HoveredFile`, `app::dropped`, and `dropped::` across `crates/` and `tools/`: `app::dropped::take` has exactly one call site, `app/frame.rs:399`, and no panel, dock, tab strip, or canvas surface reads a drop at all.

1. **A PDF onto the canvas — works, but only by accident.** `app/dropped.rs:208-210` raises `Action::Open` → `app/lifecycle.rs:62-123`, which activates an existing tab if the path is already open and otherwise `park_and_adopt`s a new one. Correct behaviour, but it is the same behaviour you get dropping on the ribbon, the status bar, or a dock splitter. `canvas/pagedrop.rs:62-67` says so explicitly: the canvas has a page-drop gap resolver and a caret and refuses to use either for a file. Dropping a PDF onto page 7 of an open drawing should offer to insert it at that gap, exactly as O67 asks of the thumbnail strip; today it silently opens a second tab.

2. **An image onto the canvas — works, but lands nowhere near the drop point.** `app/dispatch/images.rs:75-119` imports the bytes and opens the placement window (`dialog:insert-image`). The placement window's default position is used, not the pixel the operator aimed at. This is the same missing input as O67 and would be fixed by the same `filedrag::cursor_pos`: the canvas already converts screen points to page space for every other gesture.

3. **A file onto the tab strip — no target exists.** The window-wide handler opens a new tab, so it *looks* like it works, but `app/doctabs.rs` has a spring-loaded tab for PAGE drags (`doc-tab-spring`, doctabs.rs:372) and nothing whatever for file drags. There is no insertion caret between tabs, no way to say "open this beside that one", and dropping a file on a specific tab does not merge into that tab's document — which is the other reading of O67's request and arguably the more natural one.

4. **A file onto an empty window — correct, and the best-handled case.** PDF opens; an image gets `text::dropped::image_needs_a_document` (dropped.rs:220-223), which names the remedy ("Open a PDF first, or make one from the File tab"). No change needed.

5. **Multi-file drops are named but not honoured.** `app/dropped.rs:200-205` acts on the first file and records `only_the_first(n)`. Dropping four drawings onto a thumbnail strip means "import these four, in this order" — the single most likely real gesture for O67 — and today it opens one tab and apologises for the other three.

6. **`hovered_files` is dead across the whole workspace.** The only occurrence is the comment at dropped.rs:61 explaining why it was skipped. Consequently there is NO cursor feedback on the way in for any drop, anywhere — the operator gets Explorer's generic copy cursor and no indication that this window will accept the file, let alone where it will go. This is the piece that makes O67 discoverable rather than merely functional.

7. **The same defect exists WITHOUT a drop: `MergeIntoDocument` throws away a position the engine offers.** `app/actions/pages.rs:684` calls `session.merge_document(&view, InsertPosition::End)` with the position hardcoded, while `pdfcer-core/src/edit.rs:27831-27835` declares `merge_document(&mut self, source, position: InsertPosition)`. The shell has a capability the engine already ships and no route to it. Fixing O67 forces this open anyway, and once open, `pages.merge_into` could reasonably ask where — or at minimum merge at the current page rather than always at the end.

8. **Panels that should take drops and take none.** No panel reads drops, so by construction: the Attachments panel does not accept a file dropped on it as an embedded attachment; the Bookmarks panel does not accept a PDF dropped on a bookmark; the Objects panel does not accept an image dropped on a page node. I did not read those panels' sources for this row — the claim rests only on the grep showing `app::dropped` has one call site, which is sufficient to say none of them handles a drop, and insufficient to say what each of them *should* do.

What I ruled out: this is NOT a missing dispatch arm (no command id is involved — a drop never enters `dispatch_command`), NOT a missing engine verb (`insert_pages` and `merge_document` both exist and both take a position), and NOT a missing action (`PageAction::InsertPagesFromFile` already carries a path and a position). The single missing fact is the drop coordinate, and it is discarded two layers below egui, in winit's Windows `IDropTarget`.

ENGINE GAP: None in pdfcer-core or pdfcer-render. Both verbs the fix needs already exist and both already take an `InsertPosition`: `EditSession::insert_pages(&mut self, source: &DocumentView, source_pages: &[usize], position: InsertPosition) -> Result<InsertOutcome, EditError>` at D:/Dev/pdfcer/crates/pdfcer-core/src/edit.rs:28702, and `EditSession::merge_document(&mut self, source: &DocumentView, position: InsertPosition) -> Result<MergeOutcome, EditError>` at edit.rs:27831. `InsertOutcome` and `MergeOutcome` already report everything `text::pages::inserted` and `text::pages::merged` disclose. No feature request against the engine.

The gap is in the WINDOWING stack and is worth recording as an upstream issue rather than a pdfcer one. winit 0.30.13's Windows `IDropTarget` implementation receives the OLE screen-space drag point on every `DragOver` and on `Drop` and discards it (`platform_impl/windows/drop_handler.rs:109` and `:137`, both `_pt: *const POINTL`), and `WindowEvent::DroppedFile(PathBuf)` / `HoveredFile(PathBuf)` have no position field to carry it in (`winit-0.30.13/src/event.rs:176-186`). egui 0.35's `DroppedFile` and `HoveredFile` mirror that omission (`egui-0.35.0/src/data/input/dropped_file.rs:4-19`, `hovered_file.rs:4-10`). winit also emits no per-motion event during a drag-over, only one `HoveredFile` at `DragEnter`, so an insertion caret driven purely by winit events would freeze where the file entered the window. Upstream, the request is: give `DroppedFile`/`HoveredFile` a `pos: Option<Pos2>` and emit a hover event per `DragOver`. Until then the workaround is per-frame `GetCursorPos` plus a self-issued `request_repaint()`, both of which this crate can already reach — `raw-window-handle 0.6.2` is a direct dependency and `app::window_handle` (app/mod.rs:658-663) already pulls the HWND out of it.

SUMMARY: The prime suspect is innocent: the shell's decomposed page-object cache IS invalidated correctly. `OpenDoc::ensure_page_objects` is keyed on `(page_index, edit_epoch)`, the funnel bumps `edit_epoch` on every successful edit, and `pages::resync` (the O13 fix) replaces `doc.pages` on every edit — so after an insert the shell decomposes the SESSION view of the NEW page and the image is there, at the last paint-order index. It draws, it lists in the Objects panel, and `apply.rs`'s InsertImage arm even pre-selects it. The break is one layer down, in the engine. Every content-editing verb in `EditSession` — the whole vector-surgery family and the whole text-edit family — resolves the page from `page_tree::pages(&self.base)`, the BASE document, and then decomposes `ContentStream::from_page(&self.base.view(), page)` with a BASE-only XObject resolver. `add_image` appends its drawing as a NEW content stream and adds an `/XObject` resource, and both of those writes land in the session overlay (`self.state`), never in `self.base`. So the engine's model of the page is the page as it was on disk: it has N objects where the shell has N+1. The shell asks to transform/move/delete object N; the engine answers `ObjectOutOfRange { index: N, count: N }`; the funnel traces `-refused` and the operator sees a gesture that does nothing. Save and reopen makes the appended stream part of the base, `from_page` concatenates it, index N resolves, and the image edits — exactly the operator's workaround. This is not image-specific: it is every path that adds content as a new content stream, and it has a nastier sibling on the page verbs, where the base-indexed page is a DIFFERENT SHEET.

**Request: every content-editing verb in `EditSession` must resolve its page and its resources from the SESSION overlay, not from the base document.**

`EditSession` today has two page-tree readers living side by side: `EditSession::pages()` = `page_tree::pages_in(&self.graph())` (overlay, edit.rs:7932) and `page_tree::pages(&self.base)` (base, edit.rs:283). Concretely, four things are asked for:
1. The eight `page_tree::pages(&self.base)?` sites become `self.pages()?`.
2. `current_page_content`'s fallback becomes `ContentStream::from_page(&self.view(), page)`.
3. `page_content_and_objects` and `vector_plan_only` build `DocumentXObjects` / `DocumentFonts` from the session view, so a `/XObject` or `/Font` added this session classifies — without this the appended `Do` still emits nothing (decompose.rs:3023).
4. `page_objects_cache`'s key must include the page dictionary's staged state, not only the first content stream's staged span, or the memo serves a pre-insert model after an `add_image` that never touched content_id.

The known obstacle, so it is not rediscovered: `EditSession::view(&self)` (edit.rs:6999) borrows all of `self`, which is why `self.base.view()` is used inside these `&mut self` methods. The memo write and the view cannot be live at once; scoping the view and writing the cache after it drops is the smallest way through.

Second, smaller request, worth a separate row: `EditSession::page_objects(page_index)` is the natural cross-check for a shell — but it is base-derived too, so today it cannot be used to detect this skew from the outside. TWO DEFECT CLASSES generalise out of this row.

A. **A status sentence standing in for the payload.** Three live sites (clipboard.rs:522, fieldclip.rs:254, pageclip.rs:161), all writing an `os_marker` from `src/text/{clipboard,fieldclip,pageclip}.rs`. O18 did not close this class — it closed only the *collision* (text vs. object claiming one chord) via `text_owns_the_chord`. Wherever the operand is not text, a sentence is still the whole of what leaves the process, and pasting into Word gives the operator the identical experience he reported on 2026-08-21. The root cause is architectural and is named in the source itself: the marker exists ONLY because egui-winit will not deliver `Event::Paste` without clipboard text, and the shell has never opened the Windows clipboard itself. Fix that once — one `clipboard-win` transaction helper that writes the marker text AND the real formats together — and all six rows above become tractable in one place.

B. **A copy that writes nothing, which silently disables paste.** Bookmarks and markup annotations copy into `egui::Memory` and touch the OS clipboard not at all. Because `Ctrl+V` produces no event whatsoever on a textless clipboard, a bookmark copy followed by Ctrl+V does nothing — and whether it works depends on what the operator last copied in Notepad. This is the exact intermittent that clipboard.rs:500-520 and fieldclip.rs:244-253 both document in capitals, and it was fixed at two of four sites. `tools/gates/check-clipboard-chords.sh` already gates "nobody may read C/X/V as a key"; the missing sibling gate is "every function that calls `canvas::clipboard::store` must, in the same function, write the OS clipboard" — checkable by script, unlike the behaviour it protects, and it is the same "who else reads this signal?" question O18's own transferable-lesson section says was never asked.

ENGINE GAP: TWO requests, both real, neither blocking the fix.

1. **An image-extraction verb.** `pdfcer-core` can name an image (`ImageObject::xobject: Option<ObjId>`) and can decode it (`image_codec::decode_image_view`), but decoding hands back codec-raw samples with no `/Decode`, no colour-space mapping, no `/SMask` compositing — core-api 01 §11.2 says so explicitly and calls that pdfcer-render's job under rule R26. So there is no supported way to get "the image the operator is pointing at, as RGBA" other than re-rendering the page region, which re-interprets the whole content stream (~700 ms-1 s on a dense CAD sheet per docs/render-region-measurements.md) and composites anything else that overlaps the rectangle. REQUEST: `pdfcer_render::extract_image(doc, page, xobject_or_inline_index) -> Result<RenderedImage { width, height, rgba_premultiplied }, _>` — the image alone, at native sample resolution, with /Decode, colour space and /SMask applied, and nothing else in the rectangle. It is the same machinery the renderer already runs for one `Do` operator; what is missing is a door onto it. This is the difference between Acrobat's "Copy Image" (the picture) and Acrobat's "Take a Snapshot" (whatever was on screen), and the shell can only ship the second today.

2. **A vector clipboard flavour other applications read.** `ObjectClip::to_bytes` is bit-exact and pdfcer-private, and `PageClip::bytes` is a real PDF. Neither helps a paste into Word as *vector* — the Windows format for that is `CF_ENHMETAFILE`, and there is no EMF backend in pdfcer-render (grepped `emf` / `metafile` / `enhmetafile` across the crate and the shell: zero hits). REQUEST, lower priority: an EMF (or SVG, which the shell could convert) output path for a page region or an object clip. Filed as a want rather than a need — the operator asked for images, and a raster answers that.

NOT a gap: `render_page_region` already exists and is already used by this shell, and `PageClip::bytes` already being a complete PDF means the page-copy row of the generalisation table needs no engine work at all — only a Windows clipboard write the shell has never made.

GENERALISATION: The defect class is: A GESTURE WHOSE PRECONDITION IS AN AND OF TWO OR MORE INDEPENDENT STATES, SET FROM DIFFERENT SURFACES, WHERE NO SURFACE NAMES THE OTHER AND FAILURE IS SILENT. Every instance I found:

1. NODE EDITING (this row) — mode selector (Edit) AND View ▸ Navigate ▸ Points AND (status bar) pick filter Parts+Nodes. Three surfaces. `clicking.rs:336` is the AND; `dispatch.rs:641` is the silent half.

ENGINE GAP: YES, one, and it is NOT containment — containment is fully exposed and already consumed.

WHAT IS PRESENT: `pdfcer_core::vector::FormLeaf` carries `containment: Vec<ObjId>` ("outermost first, ending with the form this object is directly inside", never empty) and `paint_order: usize` (decompose.rs:1011-1045), and `hit_test_point_deep` returns leaves interleaved into page paint order. The shell consumes both (`ObjectModelProvider::containing_form`, `::containing_form_object`). So the shell CAN answer "this path is inside this Form XObject", and can name the whole chain.

WHAT IS ABSENT: **editing through recursion.** `FormLeaf::is_editable()` is a hard `false` (decompose.rs:1076-1089), with the engine's own note that it is "a method rather than a constant so that the answer has somewhere to change when editing-through-recursion is built". Every geometry verb — `move_subpath(page_index, object_index, subpath_index, dx, dy)`, `move_node(page_index, object_index, node_index, to)`, `move_nodes(page_index, object_index, moves)`, `move_handle`, `transform_objects` (02-editing-and-saving.md:1035-1042, :987) — is addressed by a PAGE paint-order index, which a leaf does not have.

THE CONSEQUENCE, EXACTLY: on any page whose drawing lives inside a form, O70's double-click chain would bottom out on geometry no verb can write. The shell already refuses honestly — `painting::draw_anchors` returns `declined("leaf-in-form-xobject")` at painting.rs:812-815 rather than drawing grab targets for a drag that must refuse, and `input::probe` offers a leaf no part and no node (input.rs:86-96). Measured scale from the provider's own table (provider/mod.rs:952-957): the print-conformance composite page 1 = 28 page objects / 4 forms / 242 leaves; ncored-benchmark-cad-drawing p1 = 129,758 / 1 / 10,256; SW41177 p1 = 5,903 / 0 / 0. So on the operator's own SolidWorks sheet nodes work and on two of the three fixtures almost nothing visible is node-editable.

FEATURE REQUEST TO THE ENGINE, in the form the shell needs it:
(1) An addressing scheme for a leaf that the geometry verbs accept — either a leaf-scoped variant (`move_nodes_in_form(page_index, form: ObjId, leaf_index, moves)`) or a widened operand on the existing verbs; the shell already carries `TargetId::Leaf(u64)` and `containment`, so it can supply either.
(2) A statement of the write semantics, because this is the hard half and it is a policy question the engine must own: writing into a form's buffer edits EVERY invocation of that form, on every page. `EditSession::unshare_form(page_index, form: ObjId)` already exists and already privatises a page's copy (and already refuses `FormNestedInAnotherForm`), so the natural contract is "node editing inside a form requires the form to be unshared first, and the verb says so by name" — which the shell can then surface as a one-click offer rather than a silent refusal.
(3) `FormLeaf::is_editable()` to become true exactly when (1) and (2) hold, so the shell's existing `page_object_index().is_none()` guards can be replaced by the engine's own predicate instead of by a proxy for it.

Until (1)-(3), the honest shell answer for O70 is: the double-click chain descends the SELECTION RUNGS of a page object (Object → Part → Node) and stops at the Object rung for anything inside a form, with `format.select_form` as the deliberate ascent — which is what ships today.

SUMMARY: DEFECT 1 is the pointer analogue of DEFECTS.md D1, and it is one function. The canvas builds its `PointerFrame` correctly — every drag/click signal comes from the acting page's own `egui::Response` (`interact.rs:377-402`) — but step 1b, `canvas::presspick::at_press`, does not. It asks the **global** `egui::Context` two questions: "did the primary button go down this frame?" (`presspick.rs:130`) and "where did it go down?" (`presspick.rs:103`), then maps that raw screen point through the page's affine transform and hit-tests it (`presspick.rs:106-112`). `viewer::screen_to_page` (`viewer/mod.rs:657-665`) is unbounded and unclamped: it converts any screen point, including one inside a docked panel, the ribbon or the status bar, into a page coordinate. When the sheet is zoomed past fit — a CAD A1 at any working zoom — the whole window maps into the page, so a press on a TextEdit in the right dock resolves to real page content and `select_only(page, object, "press")` replaces whatever was selected (`selection/mod.rs:687-704`). Defect 1 is what keeps putting him in that state: every press he makes in the panel either re-aims the object selection at whatever the panel's coordinates happen to overlay, or (when the mapped point misses) leaves it, and in the annotation case `select_only` destroys the annotation selection outright, which silently removes the markup, dimension and delete sections he was working in. FIX SHAPE: ONE guard, in one function, plus one argument threaded to it.

1. `canvas::presspick::at_press` gains a parameter — `press_owned: bool` — and both global reads are replaced:
   - `fn press_selects(ctx, tool, caps, shift)` becomes `fn press_selects(ctx, tool, caps, shift, press_owned) -> bool`, and its last line changes from `ctx.input(|i| i.pointer.button_pressed(Primary))` to `press_owned && ctx.input(|i| i.pointer.button_pressed(Primary))`. Keep both terms: `press_owned` says WHOSE press it is, `button_pressed` says it is THIS FRAME's press. Collapsing them into one would re-select on every frame the button is held, which is a different defect.
   - The origin read on presspick.rs:103 changes from `ctx.input(|i| i.pointer.press_origin())` to the Response-owned position. On the press frame `Response::interact_pointer_pos()` IS the press position (egui 0.35 context.rs:1467-1478 sets it from `input.pointer.interact_pos()` as soon as `is_pointer_button_down_on` is true), so pass that value in alongside the bool, or pass `&egui::Response` and read both from it. Passing the Response is fewer parameters and makes the ownership question unmistakable at the call site.

2. Who computes `press_owned`. The cheap form is `response.is_pointer_button_down_on()` at interact.rs:427 — one line, no struct change, and `response` is already in scope. `is_pointer_button_down_on` is set from `memory.interaction().potential_click_id/potential_drag_id`, which egui resolves with full layer and z-order awareness, so it is false for a press on a dock, on the ribbon, on the status bar, on the find bar Area, on a context-menu popup and on a modal Window — all six generalisation cases at once, with no rect arithmetic. It is true whenever ANY egui widget wants the pointer, and the canvas page widget is an egui widget, so it would be true during a legitimate canvas press. It is the pointer twin of the `egui_wants_keyboard_input()` trap DEFECTS.md D1 records, and it would suppress selection entirely. `Context::is_pointer_over_area` does not exist in 0.35 — I grepped the vendored source three ways and it is absent.
