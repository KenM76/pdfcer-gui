# ENGINE_BACKLOG.md — every capability the engine has that this shell does not reach, and the decision on each

One row per engine capability, with the verdict on it and the reason for that verdict. Read it to choose what to build next, and to find which of the engine's `[ ]` boxes are wrong.

## How this register works

**The source measurement.** `D:\Dev\pdfcer\docs\FEATURES.md` is a table whose first three columns are `core | cli | gui`. A row reading `[x]` under `core` and `[ ]` under `gui` is the engine stating, in a machine-readable place, that it has something this shell does not. `bash tools/gates/check-engine-backlog.sh` prints how many such rows exist and how many entries answer them on every run. Neither figure is derivable from the other: an entry can outlive the row it answers, and a new row can arrive with no entry at all.

**What the engine's `gui` column is worth.**

- A `[x]` is trustworthy. The engine ticks a row only when an operator can reach it in a real `pdfcer-gui` build — not when the code exists, not when a test passes.
- A `[ ]` is a negative existential and is falsifiable by nothing. No test, no gate and no compiler notices a capability arriving.
- A `[ ]` about a repository the engine does not build has no falsifier on either side and decays fastest of all.

So this register runs in both directions. Its `wanted` rows are work for us; its `shipped` rows are a report back to the engine, and sending them is part of discharging the file rather than a courtesy.

**The five verdicts.** A row's verdict is the section it sits in.

| verdict | means | and specifically |
|---|---|---|
| `wanted` | A real gap somebody should schedule. | The engine has it, an operator would use it, nobody has filed it. |
| `blocked` | Wanted, waiting on something **named**. | An operator ruling, or another surface that must exist first. The blocker is named or it is not a `blocked`. |
| `unknown` | Could not be settled, and saying so beats guessing. | An honest `unknown` is worth more than a guessed `declined`. |
| `declined` | Deliberately not a GUI surface, with the argument. | The argument is the row. A `declined` with a bare verdict is worse than no row. |
| `shipped` | The engine's `[ ]` is stale — an operator can reach it today. | The row names the surface or the call site. |

**A blocker is a measurement, and the question it measured is part of it.**
Naming the blocker is the rule this file and `NO_SURFACE.md` already state,
and it is not enough on its own. *"Blocked on `EditSession` having no verb
for it"* is a sentence whose truth changes without anybody touching this
file, and a reader holding only the name cannot tell whether it still holds
— they have to re-derive what was asked and re-ask it. Write down what was
measured and against what: which symbol was grepped, in which checkout, at
which revision. A blocker carrying its own question is falsifiable in a
minute by anybody; a blocker carrying only its answer is believed, and
being believed is how a `blocked` row outlives the thing blocking it. The
engine answers requests within hours, so the shelf life is short.

**What a `shipped` verdict rests on, and what it does not prove.** A named call site in `app::actions::*` or `panels::*` means the verb is reached through this shell's funnel — an undo entry, a cache invalidation, a disclosure — which is much stronger than a bare grep hit. It does not prove an operator can reach it: a call site behind a condition nothing sets is dead in the running program, and only `tools/ui-verify`, driving the real binary, answers that. So `shipped` here means *the engine's `[ ]` is not supported by this repository's contents*. Where a row's evidence is a driven check, the row says so.

**No row is ever deleted.** A row whose `gui` box gets ticked keeps its argument and changes section. `shipped` and `declined` are never folded together: they say opposite things to the next reader — *go and tell the engine its column is wrong* against *do not build this*.

**The gate.** `tools/gates/check-engine-backlog.sh` parses the live `FEATURES.md`, collects every `[x] core / [ ] gui` row, and fails when one is discussed nowhere here. It is deliberately weak in one direction and strong in the other: it does not judge the verdict, so a `declined` written out of laziness passes, but a capability that appears in the engine's table and is mentioned nowhere fails the build on the first `git pull` in the engine's checkout that brings it — somebody has to look at it and write a sentence, which is the whole mechanism. Its row key is a row's **opening clause**, not the whole row, because the engine's prose churns in the tail and is stable at the head. When the gate reports a row it cannot find, read its message before adding anything: a reworded row and a new row look identical to a key and are opposite acts.

**A gap this shell finds has no gate.** The gate reads the engine's table, and an absence measured here while building against the engine is not in it. Such a row has only this file. The standing habit that covers it is to triage the engine's reply channel every session; a row whose only guard is a sentence asking someone to re-verify it needs a scheduled re-verification, not a better sentence. The same blindness runs the other way: a capability whose `gui` column is already `[x]` can still be half reachable, and no gate in this project can tell.

**The tally.** Run `python tools/walk-engine-backlog.py`. It counts the rows under each `## \`verdict\`` heading, compares them against the figure that heading claims, and prints which one disagrees. `--at HEAD` walks what is committed rather than the working tree, which is how *rows this session added* are told apart from *rows that were already uncounted*. `--check` exits non-zero on a disagreement or an over-cap row. When you file a row, run `python tools/walk-engine-backlog.py --write YYYY-MM-DD` **in the same edit**: it rewrites all five headings from the walk it just did, keeping each heading's sub-label verbatim, so no hand edit is left to get wrong. Re-walk, never increment — a figure obtained by arithmetic from a figure nobody re-measured is not a measurement.

**A row is a verdict plus one paragraph**, capped at 1200 characters and enforced by `--check`. Cut the narration of how a conclusion was reached, the restatements and the quotations; keep the opening clause verbatim (the gate keys on it), the verdict, the one load-bearing reason, and the anchors somebody would need to find the work.

**What those two instruments do not measure.** Both count a row by the section it sits in, never by the verdict its body states. They prove each capability is *accounted for* and prove nothing about whether the account is true. `--check` additionally reports rows whose opening clause names a verdict other than their section's; it reports rather than fails, because a partly consumed row can legitimately open with a tick.

**The third instrument, which falsifies the absence itself.** `python tools/check-backlog-verdict-drift.py` takes the engine symbols named in the first cell of every `wanted` and `blocked` row — the only two verdicts that assert an absence — and looks for them in `crates/pdfcer-gui/src`. A hit means the source contradicts the register, and it fails. `.ident` counts a method call **and a field read**, because `SignReport::appearance_lines` is consumed as a field and that is exactly how its row stayed `wanted` after it shipped; a bare identifier counts only inside a file that imports it from an engine crate, because an absence claim has to name the **receiver** — every `page_objects` hit in this repository is our own `OpenDoc::page_objects`, never the engine's. An exemption is per SYMBOL and never per row — `<!--namesake:IDENT-->` with the reason beside it — because a row-wide mute would hide the day that row's other symbols get wired, and the exempt count prints on every clean run. A register wrong in the *shipped* direction is worse than one that is incomplete: it schedules work already done, and under-reports the program to the person who paid for it.

## Standing instructions

**Pass 72.0 — the shell's parallel true-removal proof is mandatory, not merely careful.** `pdfcer_core::redact::apply_redactions` returns `Result<(Vec<u8>, RedactionReport), RedactError>` — a report, not a verdict — and `RedactionVerdict` and `verify_redaction` appear nowhere in `pdfcer-core`. Pass 72.0 has therefore not closed. **When core lands the verdict type this becomes a DELETION, not a parallel implementation**: watch the request channel for the `note_` announcing Pass 72.0 closed and file the migration as its own task. `redact::sealed`'s syn-based call-site monopoly assertion — exactly one file, exactly twice, failing closed on zero as well as on three — is what will make that migration visible rather than gradual.
